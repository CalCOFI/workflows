## The ask (Ben, 2026-09-05)

calcofi.io groups *products* as cards; nothing on it is a **dataset**. The apps have tried to make datasets
stand out (Explorer pills and Sources line, Station Explorer's coverage, Hexagon Explorer's labels) but their
space is already crammed. calcofi.org/data has the appealing overview — icon tiles that dive into dataset
types and link out to EDI, ERDDAP or a download — but it is hand-maintained by another team, not data-driven,
and has no search or filtering. Meanwhile calcofi.io has grown *many* endpoints per dataset (content-addressed
parquet, ERDDAP, CF netCDF, the apps, R and Python, OBIS-in-progress, EDI/NCEI upstream, Zenodo release DOIs)
and **there is no single view of a dataset where all of them appear.** Ben wants a plan that (1) makes calcofi.io
dataset-centric while still highlighting the integrated database, its schema, and SQL / R / Python access;
(2) takes `docs/portals.qmd` seriously — every external portal CalCOFI wants to be in, linked centrally; and
(3) weighs the catalog software (CKAN as IOOS runs it, GeoNetwork, GeoNode, pycsw, geOrchestra, OpenDataCat)
and the spatial query standards (CSW, WMS/WFS, STAC) against *not* running another set of containers.

## Context — what exists today (measured 2026-09-05)

### The landing page is product-centric

`CalCOFI.github.io/_data/products.yml` drives **26 cards in 5 sections** — Apps 5 · Apps-Dataset 3 ·
Services 2 · Developer 7 · Students 9. The word *dataset* appears once, in a section title. A visitor who
wants "the CTD data" has to know that *CTD Transects*, *CTD Explorer*, `calcofi_ctd-cast` on ERDDAP, the
`obs_env` partitions, `calcofi_ctd-cast.nc` and `cc_get_db()` are the same thing. Nothing tells them.

### The software survey, for this use

| option | what it is | what it would cost here | verdict |
|---|---|---|---|
| **CKAN as IOOS runs it** (`ioos/catalog-docker-base`, `ckanext-ioos-theme`) | CKAN 2.10 + Solr + PostgreSQL + Redis + pycsw + datapusher + harvest gather/fetch workers — **8+ containers**; harvests ISO WAFs/CSW; ISO-centric dataset pages; 409 commits, AGPL | a second stack to patch, a Solr to keep warm, a Python 2→3-era codebase; our records would round-trip *through* ISO XML to get into it | **No.** Its harvester is the value — and it can harvest *us* (below) |
| **GeoNetwork** | Java + Elasticsearch ISO 19115/19139 catalog with an editor and CSW/OGC API Records | 2 containers, an ISO-first editing model we do not need (the record is generated, not edited) | No |
| **GeoNode** / **geOrchestra** | full SDIs (GeoServer + catalog + auth + map composer) | 5–10 containers; solves problems we do not have (upload, editing, users) | No |
| **OpenDataCat** (GeoCat, on GeoNetwork) | a newer catalog UI over GeoNetwork; INSPIRE-oriented | as GeoNetwork; commercial support model | No |
| **pycsw 3** | one Python process: CSW 2/3, **OGC API – Records**, **STAC API** (`/stac/search`, CQL2), OpenSearch, OAI-PMH, SRU; SQLite or PostgreSQL repository; OGC reference implementation; MIT | one small container fed by `pycsw-admin load_records` from ISO/JSON we generate; it is the CSW *inside* the IOOS stack | **Later, gated** — the only option that adds an endpoint we cannot make static (CSW). Not needed for IOOS harvesting, which reads ERDDAP's WAF |
| **pygeoapi** | OGC API Features / Records / Tiles / EDR from files or databases | one container; Records over a GeoJSON of our records; Features over `grid.geojson`; EDR (position/area/cube over CTD) is genuinely interesting but a different plan | Not for the catalog; note EDR for a future *services* plan |
| **STAC, static** | Catalog → Collection → Item as plain JSON on object storage; the `table` extension describes tabular assets (parquet columns); `stac-browser` is a Vue SPA that browses a static root; DuckDB's `stac` extension reads a catalog as a table | zero servers; generated at release next to `catalog.json`; hosted on GCS + GitHub Pages | **Yes** — the modern JSON catalog API, at the cost of a generator |
| **schema.org JSON-LD + sitemap** | what Google Dataset Search and ODIS crawl | one `<script type="application/ld+json">` per page + `sitemap.xml` | **Yes** — already the strategy in `portals.qmd`; only the pages were missing |
| **DCAT-US `data.json`** | what data.gov and every CKAN can harvest | one generated file | **Yes** — cheap, and CKAN-harvestable without running CKAN |
| **WMS/WFS** | rendered / feature layers | `tile.calcofi.io` (pg_tileserv, legacy `gis` db) and the Explorer's PMTiles registry already serve the spatial layers; OGC API Features would be pygeoapi | Out of scope here; the catalog *lists* the layers and their tile/GeoJSON URLs |

The pattern the survey points at: **the record is ours and generated; the discovery endpoints are static
files in standard shapes; the search UIs that need servers already exist elsewhere and can be pointed at us
(IOOS ↔ ERDDAP WAF, ODIS ↔ sitemap + JSON-LD, Google ↔ JSON-LD, data.gov/CKAN ↔ data.json, OBIS ↔ IPT).**

## Goal

1. **One record per dataset**, generated at release from the sidecars and registries, validated like the
   citation contract, published as `datasets.json` beside `catalog.json` — the *single* dataset list every
   product reads (the six partial lists collapse onto it).
2. **One page per dataset** at `https://calcofi.io/datasets/{dataset_key}/` — the "single view" — with every
   endpoint grouped by *how you want it* (explore · query · code · download · services · archives · cite ·
   provenance), coverage drawn from `coverage.json`, and schema.org JSON-LD in the page.
3. **The front door re-cut around Datasets**: calcofi.io opens on the dataset catalog (twelve category tiles
   with the brand icons — the calcofi.org idea, made data-driven and searchable), with the integrated database
   as its spine (release, DOI, schema, SQL / R / Python), and the products re-framed as *ways to use the data*,
   each card naming the datasets it serves.
4. **Machine catalogs without servers**: JSON-LD + `sitemap.xml` (ODIS, Google), DCAT-US `data.json`, a static
   STAC catalog with `stac-browser`; and **registrations** of what already exists — ERDDAP's ISO WAF with the
   IOOS Catalog, the calcofi.io sitemap with ODIS.
5. **The portal gaps made visible and worked**: each dataset page shows its OBIS / EDI / NCEI / ERDDAP status
   from the registry, so the catalog is also the progress board; the publications that are missing (the nine
   other biological datasets to OBIS, the program's own datasets to EDI) come from **one EML document per
   dataset** feeding generic publishers (D-8), uploaded when the data change.

## Non-goals

- Running CKAN, GeoNetwork, GeoNode or geOrchestra. pycsw is a gated option (Decision 9), not a phase.
- Re-designing any app's interior. The apps gain *links to* dataset pages and a `datasets:` declaration.
- Replacing calcofi.org/data. It keeps the public narrative; the catalog is where access lives (Decision 8).
- Per-dataset DOIs minted by calcofi.io. A dataset's DOI comes from its archive (EDI, NCEI, UCSD Library,
  Zenodo for the release); the catalog *records* DOIs, it does not create them.
- Versioned dataset pages. The page renders the promoted release; older records stay browsable through the
  version folders on GCS and db-schema's picker (a `?v=` on the page is a later, small addition).
- Editing metadata in a UI. The record is generated from YAML/CSV under review, as everything else is.

## Design

### D-1 · The unit is `dataset_key`; the record is generated, not authored on the landing page

`calcofi4db::build_dataset_catalog(con, meta, coverage, catalog, registries)` runs in `release_database.qmd`
after `merge_metadata_json()` and `build_coverage()`, and writes **`datasets.json`** (schema 1.0, Appendix A)
into the release folder. It joins, per `dataset_key`:

- the `metadata.json` dataset block (identity, description, attribution, links, tables, workflow);
- `coverage.json` rolled up: `n_obs`, `n_roots`, `year_min/max`, `years[]` (the sparkline), `n_stations`
  (stations whose `datasets[]` include it), `n_variables` + the variable keys, `n_taxa`, depth range;
- `catalog.json` objects that belong to the dataset — the `obs`/`obs_env` partitions filed under it and the
  whole tables it owns (`tables[]`) — each with `path`, `bytes`, `sha256`, `since`; `since_version` (first
  release the dataset appeared in, from the sidecars of `versions.json`);
- **distributions[]** — the measured endpoints: ERDDAP ids that exist on erddap.calcofi.io *now* (from
  `allDatasets`, matched on the `dataset_key` prefix; a legacy id is listed under its dataset with
  `legacy: true`), the netCDF `manifests.json` → latest `canonical_url` + `sha256` + `bytes`, the parquet
  objects, the ingest notebook, the source portal (`link_data_source`, classified by host into
  `edi | ncei | erddap-noaa | datazoo | ucsd-library | calcofi.org | other`), the calcofi.org page, and the
  *curated* externals from a new registry `metadata/distribution.csv` (`dataset_key, kind, portal, url, title,
  status, notes` — e.g. `swfsc_ichthyo` ↔ CoastWatch `erdCalCOFIlrvcnt` … `erdCalCOFItows`, EDI `edi.109.4`;
  `farallon_bird-mammal` ↔ EDI `knb-lter-cce.255.3`; `cce-lter_picoplankton-bacteria` ↔ EDI 159.7);
- **registrations[]** — from `dataset_status.csv`'s `publish_obis` / `publish_erddap` / `publish_edi` columns
  (a fourth, `publish_ncei`, is added): `{portal, status: published | planned | n/a, issue, url}`;
- **status** — `stage`, `priority`, `gh_issue`, `blockers`, `updated`, and `questions_open` counted from the
  dataset's `questions.csv`.

`check_dataset_catalog()` fails the release when a record lacks `dataset_name`, `category` (must be in
`category.csv`), `provider` (in `provider.csv`), `description`, `coverage_bbox`, at least one *download*
distribution, and — the same rule as the citation contract — a `citation_main` or an open question that

  source are listed and resolved with their owners: historical duplicates are retired or cross-referenced, and a
  dataset whose authority is CCE-LTER (or NOAA) is never republished by CalCOFI without that provider's yes.
- **EDI, and what a *scope* is** (Ben's Q5). An EDI package id is `scope.identifier.revision`
  (`knb-lter-cce.254.4`, `edi.109.4`). A scope is a **namespace, not an organisation account**: LTER sites own
  theirs (`knb-lter-cce` is CCE-LTER's, curated by their information manager), and **`edi` is the open scope any
  registered user publishes under** — no organisational registration, no curation rights over anyone else's
  packages; the account that creates a package owns it and grants others read/write through the EML `access`
  element. EDI does **not** forward to NCEI: NCEI is a separate deposit (Send2NCEI or an NCEI data manager, via
  SWFSC for NOAA-collected data) with its own DOI — a separate thread, as Ben says. What EDI gives that ERDDAP
  cannot is the *whole* package, archived and versioned: every entity, any file type (the tables as `dataTable`
  with `attributeList`; the parquet and `catalog.json` as `otherEntity`), a DOI per revision, PASTA's quality
  checks, DataONE indexing. The automation is real: `EDIutils` (`login()`, `evaluate_data_package()`,
  `create_data_package()`, `update_data_package()` — a new revision per release), against EDI's **staging**
  environment first (`env = "staging"`), the EML from `build_eml()` (D-8). *Recommend: scope `edi`, one package
  per integrated dataset, owner a CalCOFI EDI account Erin holds with Ben as editor; CCE-LTER's `knb-lter-cce`
  packages stay theirs, linked as sources, never republished — the same non-interference rule as OBIS.*
  For the program's own datasets with no archive and no DOI (bottle, ctd-cast, mets, later
  ichthyo): an EDI data package per dataset per release — the release's own `eml/{dataset_key}.xml` (D-8) plus
  data entities exported from the dataset's core tables with an `attributeList` from `metadata.json` — built by
  a generic `publish_to-edi.qmd` and pushed through PASTA (`EDIutils`) only under an explicit flag, like the IPT. Whether CalCOFI publishes under its own EDI scope or through CCE-LTER's
  is Open question 5. NCEI (Send2NCEI, via SWFSC) is the NOAA-side alternative for the same three — Ed's DMP
  thread.
- **ERDDAP** — done for all 16; the 7 legacy ids get `retired` rows in `distribution.csv` and a sunset date.

### D-11 · Holdings are datasets without a release yet — same key, same sidecar, same Sheet, same weekly observation

Ben's question (2026-09-05): how are the planned and external datasets managed with Sheets and programmatic
checking, not just listed? The answer is to give them **no special machinery**:

- **Same key.** Every holding gets a `dataset_key` = `{provider}_{dataset}` from the registries
  (`cce-lter_hplc-pigments`, `cce-lter_poc-pon`, `jcvi_ncog-metabarcoding`, `calpoly_whale-edna`,
  `stanford_hopkins-zooplankton`, `sccoos_ifcb-ctd` …). A new provider is one row in `provider.csv` (JCVI, Cal
  Poly, Stanford Hopkins Marine Station). `holdings.csv` becomes an **index generated from the sidecars**, not a
  second place to type.
- **Same sidecar.** `metadata/{provider}/{dataset}/dataset_meta.yml` exists for a holding exactly as for an
  ingested dataset, with `status: planned | external | archived` (and `priority`, `gh_issue`, `next_step`,
  `owner`) in place of the release-derived blocks. When a holding is ingested, the notebook is added and the
  sidecar is already there — no metadata is re-entered, the tile's grey row becomes a full row on the next
  release, and the page URL never changes.
- **Same Sheet.** A holding appears in its provider's `metadata` tab like any dataset (CCE-LTER's tab gains
  POC/PON, TOC, HPLC, isotopes, cetaceans; small providers get a Sheet each — cheap). The CalCOFI team's own
  tab (`calcofi` Sheet, tab `holdings`) is the **triage board**: every holding with `status`, `priority`,
  `owner`, `next_step`, `gh_issue`, the observed state — Erin's and Betty's working view, replacing the CalOOS
  sheet for internal tracking; `sync_dataset_meta_sheets.R` pushes and pulls it with the same protected-column
  rule (`status`, `priority`, `owner`, `next_step` editable there).
- **Same weekly observation.** `observe_distributions()` (D-10) covers holdings' links and DOIs too, and
  `portal.csv` gains an `observe_method` per portal: `edi-pasta` (newest revision + `pubDate` from
  `pasta.lternet.edu/package/eml/{scope}/{id}`), `doi` (doi.org resolves), `obis-api` (`updated`),
  `ncbi-esummary` (BioProject registration and sample counts), `zenodo-api` (`version`, `updated`),
  `erddap-das` (`date_modified`, `time_coverage_end`), `caloos` / `http` (liveness by ranged GET). A GitHub
  Action `observe.yml` in `workflows` runs it weekly and on demand and commits `distribution_observed.json`.
- **`visibility: public | internal` on every sidecar — a checkbox in the Sheet** (Ben, 2026-09-05). `internal`
  keeps a dataset in the record and on the triage board but out of every public surface (pages, sitemap,
  `data.json`, STAC, `cc_datasets()` by default) until the conversation with its provider has been had.
- **A change is a proposal, never a silent edit.** A new EDI revision, a dead link, a DOI newly minted (the
  crab deposit), an ERDDAP `time_coverage_end` past the last ingest's `source_accessed` → one row in the
  provider's `questions.csv` (`observed_change`, `proposed`) and the same line in the `holdings` tab; the
  dataset page shows *source updated after last ingest* (integrated) or *external record updated* (holding)
  from the observed file. The sitemap and `registrations[]` read the same file (D-10).

### D-8 · One EML document per dataset; every publisher reads it

`publish_ichthyo_to-obis.qmd` already builds a valid EML 2.2 document with the `EML` package
(`write_eml()` + `eml_validate()`), but from hand-typed strings inside the notebook: sampling methods, study
extent, sampling description, rights, funding. Those strings are dataset *metadata*, and today they live in
the one place a provider cannot edit and the record cannot see. The plan moves them into the record and makes
EML the one metadata document the portals share:

- **`calcofi4db::build_eml(record)`** turns a `datasets.json` record into EML at release time —
  `eml/{dataset_key}.xml` in the release folder, validated by `eml_validate()`, a release gate like
  `check_dataset_catalog()`. Field by field: `title` ← `dataset_name`; `abstract` ← `description_md`
  (rendered to text); `creator` / `contact` / `metadataProvider` ← `creators[]` (name, organization, ORCID,
  email; from the descriptive sidecar, D-9) with the CalCOFI role address as the fallback contact;
  `pubDate` ← `release_date`; `keywordSet` ← `keywords` (GCMD) + the category + the variable names;
  `intellectualRights` ← `license` / `license_url` from `license.csv`; `coverage` — geographic from
  `coverage_bbox`, temporal from `year_min/max`, taxonomic from `coverage.taxa[]` (the WoRMS-resolved names);
  `methods/methodStep` and `sampling/studyExtent` + `samplingDescription` ← the narrative fields of the
  sidecar, with `gear.csv`'s `dwc_samplingProtocol` sentences appended for the dataset's `tow_type`s;
  `project/funding` ← `acknowledgement`; `dataTable[]` ← the dataset's core tables with `attributeList` from
  `metadata.json` columns (units, descriptions) — the entity list EDI needs and the IPT ignores;
  `alternateIdentifier` ← the DOI and the dataset page URL; `additionalMetadata` ← the release citation.
- **`publish_to-obis.qmd`** (generic, superseding `publish_ichthyo_to-obis.qmd`; folds in the 2026-09-03
  follow-on `plans_todo/2026-09-03 Follow-on — generic publish_to-obis over the core.md`). The ichthyo notebook
  is the last per-dataset publisher: it reads the `swfsc_ichthyo` source tables directly (`tbl_ichthyo`,
  `net_uuid`, `species_id`, the `lookup` stage tables) and hand-builds the Event / Occurrence / eMoF triple,
  which is why nine other biological datasets have no OBIS route at all. Everything it hand-builds now exists
  generically in the core, so the notebook is parameterised by `dataset_key` over `cc_get_db()` + the catalog
  (the `publish_obis_template.qmd` scaffold and the generic netCDF / ERDDAP pair are the pattern):

  | Darwin Core | from the core | vocabulary |
  |---|---|---|
  | Event core — `eventID`, `parentEventID`, `eventDate`, `decimalLatitude/Longitude`, `minimum/maximumDepthInMeters`, `sampleSizeValue/Unit`, `samplingProtocol`, `locationID` | `sample`'s adjacency list — `sample_key`, `parent_sample_key`, `datetime`, `latitude`/`longitude`, `depth_min_m`/`depth_max_m`, `volume_sampled_m3`, `tow_type`, `site_key` | `gear.csv` `dwc_samplingProtocol` + NERC L22 |

  — so absences come from `sample_root` minus the positives (a tow that was sorted for the taxon and found
  none), never from zero-valued rows; a dataset that records its zeros (the crab's examined-and-empty tows)

  the output: `data/darwincore/{dataset_key}/{dataset_key}_{version}.zip` + a manifest (`content_hash`,

  the old notebook is retired. Which datasets publish, under which licence, and one IPT resource per dataset
  or one for the programme are Ben's and the providers' call (Open question 9); the follow-on's warning
  stands — republishing a dataset whose OBIS record a provider already owns needs that provider's yes first.
- **Upload is a deliberate act, gated on change.** The notebook is *in* `_targets.R` (it only writes files);

### D-9 · Providers edit metadata in a Google Sheet; git keeps the record

The questions registry already has the pattern (`scripts/sync_questions_sheets.R`, `metadata/questions_sheets.yml`):
one Sheet per provider, generated from CSVs in git, only the columns a provider may edit unprotected, `pull`
writes those columns back. Dataset metadata gets the same treatment:

- **The descriptive fields move out of the notebook YAML into a sidecar** the sheet can round-trip:
  `metadata/{provider}/{dataset}/dataset_meta.yml` — `abstract` (= `description_md`), `methods_md`,
  `study_extent`, `sampling_description`, `creators[]` (name, organization, orcid, email, role), `contact`,
  `keywords[]`, `acknowledgement`, `citation_main`, `citation_others`, `license`, `license_url`, `doi`,
  `pi_names`, `link_calcofi_org`, `link_data_source`. The ingest's `calcofi.dataset_meta` block keeps the
  *structural* keys only (`provider`, `dataset`, `dataset_name`, `dataset_name_short`, `category`, `tables`,
  `in_release`); `read_ingest_yaml()` merges the two, and `build_workflows_index.R` errors if a descriptive
  key still sits in a notebook. A one-off `scripts/migrate_dataset_meta.R` moves the current values.
- **Each provider's existing Sheet gains a `metadata` tab** in long form — one row per (dataset, field):
  `dataset_key · field · value · guidance · edited_by · edited_date` — because abstracts and methods are
  paragraphs, and a paragraph in a wide-table cell is unreadable. `guidance` is the one-line help per field
  (what EML/OBIS/EDI need it for, an example). Only `value`, `edited_by` and `edited_date` are unprotected.
  `scripts/sync_dataset_meta_sheets.R push|pull [provider] [--execute]` mirrors the questions script (same
  auth, same dry-run default, same tests); `pull` writes `value` back into the sidecar and stamps
  `edited_by/edited_date`, and the citation/licence checks run on the pulled values before anything is
  committed — a licence outside `license.csv` is refused at pull, not at release.
- **Fields are tiered so a provider is not overwhelmed** (Ben, 2026-09-05). `metadata/dataset_meta_fields.csv`
  carries `importance: required | recommended | optional` and `eml_path`, taken from EDI's EML best practices
  and ezEML's required set — *required*: title, abstract, creators, contact, licence, keywords, geographic +
  temporal coverage, methods, data entities; *recommended*: acknowledgement/funding, associated parties,
  quality control, maintenance, citation, DOI; *optional*: the rest. The tab sorts required rows first under
  a coloured header band per tier (or three tabs side by side), and `license` **is** editable there,
  validated at pull against `license.csv`. Borrow field names from `lkuiucsb/Excel-to-EML` where they fit —
  its workbook is the nearest existing sheet-to-EML shape; the other references are rOpenSci `EML`, the ezEML
  user guide, `EMLaide`, EDI's data-entities chapter and Palmer LTER's ezEML guidebook.
- **Measured fields never appear in the sheet.** Coverage, counts, `source_accessed`, DOIs that resolve — the
  record measures those; the sheet shows them read-only beside the editable rows so a provider sees what
  the catalog will say.
- The same tab is where the pending attribution holes surface as rows to fill: today `contact` 0/16,
  `acknowledgement` 3/16, `citation_main` 11/16 — with the `questions.csv` row that tracks each.
- **The CalOOS working sheet is imported, not re-typed.** `scripts/import_caloos_sheet.R` reads the public CSV
  export, maps its columns onto the sidecar (*Lead contributor name/email/affiliation* → `creators[]` +
  `contact`; *Preferred citation* → `citation_main` proposal; *License/Usage* → a `license.csv` id proposal
  ("Public domain (CC0)" → `CC0-1.0`, checked against the ERDDAP `.das` `license` global); *Tags* → `keywords`
  alongside GCMD; *Funders* → `funding`; *contributors by role* → `associated_parties[]`; *QC flags + protocol* →
  `quality_control_md`; *Update frequency*, *Ongoing v. archived*, *Continuous* → `maintenance`; *Dataset
  Abstract* → an `abstract` proposal where the sidecar's is shorter) and writes **proposals** into each
  sidecar with `# source: caloos-sheet, row N, 2026-09-05` comments, never silently over an existing value; the
  diff is the hand-back. Erin and Betty keep working in the sheet until the per-provider tabs are pushed with
  its content already in them; afterwards the sheet remains CalOOS's submission form, generated from the
  record if CalOOS wants it refreshed.

### D-10 · The ODIS sitemap follows the record, and supersession is tracked

`update_datasets-sitemap.qmd` today lists 78 *external* dataset pages from a hand-maintained Google Sheet
of repositories (snapshot 2025-07-02), with `lastmod` = the run date. It becomes a **generated view of
`datasets.json`**:

- `distribution.csv` (D-1) gains `status: current | superseded | retired` and `superseded_by` (a URL or a
  `dataset_key`), plus `observed_utc`. **Observed, not asserted, where a portal has an API**: EDI's PASTA
  lists a package's revisions (so `knb-lter-cce.183.2` is `superseded_by knb-lter-cce.262` the way its own
  title says), OBIS's dataset API carries `updated`, ERDDAP's `allDatasets` says what is served now;
  `calcofi4db::observe_distributions()` refreshes `metadata/distribution_observed.json` weekly and at release,
  and a distribution the authority no longer answers for becomes `retired` with the date — nothing is
  deleted from the registry, so the page can say "was at X until 2026-08; now at Y".
- **`datasets/sitemap.xml` = the calcofi.io dataset pages (canonical, `lastmod` = the release date or the
  sidecar's `edited_date`, whichever is later) + every `current` external record of a CalCOFI dataset (EDI
  package latest revision, the OBIS dataset page, the IPT resource, ERDDAP `info` pages on calcofi.io and
  CoastWatch), never a `superseded` or `retired` one.** The JSON-LD on each page carries the same external
  records as `sameAs`, so a crawler meeting the record twice can tell it is one dataset.
- The sitemap regenerates on every `datasets.json` change (release dispatch) and weekly (a portal can
  revise a package without a release). ODISCat record 3318 points at this file (D-5.1). The old repository
  Sheet is retired; `holdings.csv` + `distribution.csv` replace it, in git, reviewed.

## Risks and what bounds them

- **Two truths.** `products.yml` and `datasets.json` could drift. Bounded by the build failing on an unknown
  key, and by `datasets.json` being the only source of dataset facts (products carry keys, never names).
- **Stale endpoints.** A legacy ERDDAP id or a moved source URL listed on a page is worse than absence.
  Bounded by the HEAD check at release and a weekly `refresh.yml` link check that opens an issue on failure.
- **ISO 19115-3 vs the IOOS harvester.** ERDDAP 2.30 emits 19115-3; ckanext-spatial's parser may want
  19139. Bounded by asking IOOS before registering and by the FGDC WAF / generated-19139 fallback (D-5.4).
- **The registration wall.** Linking an open ERDDAP beside a walled calcofi.org download exposes a policy
  gap. Bounded by raising it now (Open question 1) — the catalog reports both honestly either way.
- **STAC for tabular data is young.** The `table` extension is stable but few tools read it. Bounded by
  scoping STAC as a machine bonus (Phase 3), never the UI the catalog depends on.
- **Attribution holes go public.** Five datasets without a citation, none with a contact, become visible
  on their pages. That is the point — the page shows "citation pending: question Q_ open" rather than
  inventing one — but Erin should see the pages before the flip.
- **calcofi.org timing.** The SIO rebuild may land before or after Phase 1. Bounded by the dataset page URLs
  being stable from day one (`dataset_key` never changes), so the tiles can link whenever they are built.
- **Jekyll plugins on Pages.** Custom plugins need the Actions build, which the site already uses; the
  fallback is generating the pages in `fetch_release.sh` (a 60-line Python step) instead.
