Summary

Duncan Watson-Parris asked for a pilot of the benchmark proposed in Aim 2: about 20–30 questions about the data, put to off-the-shelf models, with performance summarized in a sentence or two as preliminary data. This notebook runs that pilot and keeps every step reproducible.

We put 24 questions to 5 model × effort configurations, 3 times each, under three conditions:

  • closed-book: no tools and no data, so the model answers from training alone.
  • raw: the providers’ public sources, as a user finds them today (ERDDAP, CalCOFI.org, EDI, NCEI). This is the pilot’s stand-in for the proposal’s “release 0”.
  • release: integrated release v2026.10.21 as a local DuckDB database, with no network.

Accuracy across configurations:

  • closed-book: 12–31%
  • raw: 76–96%
  • release: 89–96%

Why this pilot

The proposal’s Aim 2 scores the data, not the agent. Existing benchmarks for data-driven science hold the data fixed and compare agents: DiscoveryBench (Majumder et al., 2024), BLADE (Gu et al., 2024) and ScienceAgentBench (Chen et al., 2025). Aim 2 instead holds the agent fixed and asks how much each release improves what it can do. Five AI reviewers of the draft (punch-list row 2) said a small pilot would be the strongest preliminary result the text could add. This pilot reproduces the Aim 2 design at small scale:

  • the three tiers of questions, plus traps and unanswerable items
  • reference answers written as code
  • repeated runs on several pinned models and effort levels
  • a closed-book condition
  • a raw-source baseline

  datatable(rownames = FALSE, options = list(pageLength = 30, dom = "t"))

Questions. There are eight retrieval questions (one value from one dataset) and seven integration questions that join datasets at the same cruise and station:

  • bottle × ichthyoplankton
  • ZooScan × bottle
  • CTD × ichthyoplankton
  • the cruise and ship reference
  • a taxonomic join between the ichthyoplankton and mesopelagic-fish datasets

There are six analysis questions:

  • anomalies relative to a 1993–2013 station-by-month baseline
  • linear trends
  • a mean larval density where tows with no catch must count as zero. The ichthyoplankton records list only positive catches, so this one is a trap.
  • a correlation

Three questions cannot be answered from the data:

  • nitrate before 1959
  • bottle pH in 1985
  • CalBOBL bongo tows in 1972, before the bongo net replaced the ring net in 1977–78

The reference SQL for each question is in libs/bench_ai_readiness/questions.yml.

Reference answers are the question’s SQL run on the release. Where the raw sessions agreed with each other and disagreed with the release, we traced the difference to its source. In one case (finding 4 under Raw vs. release disagreements) the release was wrong, and the reference SQL now corrects for it. Elsewhere a legitimate difference between a provider’s file and the release still scores the raw answer wrong, so the pilot stays conservative for the raw condition.

Sessions. Each session is one headless Claude Code run (claude -p, version 2.1.314). It loads no CLAUDE.md, memory, skills or MCP servers, and runs inside Claude Code’s OS sandbox:

  • it can write only to its own folder
  • it cannot read the CalCOFI repositories, the other condition’s runs or, in the raw condition, the release copy
  • network access is limited to the providers’ domains in the raw condition, and is off in the release condition

Every tool call is checked afterwards for any reach past the session’s condition (Table 5). A session had 4 min (closed), 20 min (release) or 40 min (raw), and had to end with FINAL ANSWER: <value> or FINAL ANSWER: NOT AVAILABLE. Numbers are scored within the tolerance stated per question, and unanswerable items only by declining. The runner is libs/bench_ai_readiness/run_agents.sh and the scorer is libs/bench_ai_readiness/score.R.

Raw vs. release disagreements

Code 
f_notes <- file.path(dir_out, glue("notes_{run_tag}.md"))
if (file.exists(f_notes)) cat(readLines(f_notes), sep = "\n")

Changes made during the run (2026-10-30), recorded so the protocol is honest about them.

  1. The raw-condition allowlist was widened, and every raw session was re-run. The first Sonnet 5.5 raw sessions were refused at hosts that serve the providers’ own data:

    • ccelter.ucsd.edu (CCE-LTER ZooScan)
    • library.ucsd.edu (UC San Diego Library Digital Collections, which holds the SIO mesopelagic fish data)
    • doi.org
    • DataONE
    • CeNCOOS ERDDAP

    Those failures measured the sandbox, not the data. All raw sessions from before the fix were deleted and run again with the allowlist now in run_agents.sh.

  2. The bottle quality rule was made explicit in 10 questions (R1, R4, I1, I4, I6, A1, A2, A3, A5, A6), and they were re-run for every configuration. The first wording said “unflagged”. In the bottle database, quality codes 0–5 and 7 are undocumented, 6 means “OK, taken from CTD”, and only 8 (suspect) and 9 (missing) mark bad values. The reference (qual_ok) excludes only 8 and 9, but some sessions read “unflagged” as “no code at all”. On I6 that gives 0.601 rather than 0.458 µmol/L, because the code-4 nitrate values are all 0. The questions now state the rule. The ambiguity is itself a finding for Aim 1: a bottle quality-code vocabulary in which most codes are undocumented costs an AI user (and a human one) a correct answer.

  3. U3 is scored as declared, which is strict. U3 asks how many anchovy larvae were counted in CB bongo tows in 1972. The bongo net replaced the ring net in 1977–78, so no CB tows exist that year. Raw sessions that found this, said so, and still answered “0” are scored wrong, because the pre-declared rule for unanswerable items is to decline. The by-question table shows how many U3 answers were “0” rather than NOT AVAILABLE.

  4. The raw sessions found a defect in the release, and the I1 and I2 references were corrected. On I1, every raw session agreed on 14.47 °C, and on I2 most raw sessions said 1030, against the release’s 14.36 °C and 1010. The raw agents were right. Release v2026.10.21 holds the July 2009 cruise twice, with the same dates under two keys:

    • 2009-07-31M4 “MCARTHUR”, derived from the bottle and picoplankton data.
    • 2009-07-33MH “MCARTHUR II”, the SWFSC reference used by ichthyo, CTD, ZooScan, PIC, seabirds and phytoplankton.

    No bottle cast from that cruise joins to anything else, and check_cruise_key_integrity() did not catch it. The reference SQL for I1 and I2 now maps the bottle key to the SWFSC key (commented in questions.yml), so it matches the providers’ own cruise and station. Release sessions that trusted the release’s key are scored against the corrected value:

    • I1 moves out of tolerance (14.36 vs 14.47, tolerance 0.1 °C).
    • I2 stays inside it (1010 vs 1030, tolerance 5%).

    This is the benchmark doing its job. A fix in the next release should raise the release condition’s score on exactly these items, which is the per-release comparison Aim 2 proposes.

  5. R7 (dissolved iron) is behind a login at the provider. No raw session answered R7. EDI refuses public reads of package knb-lter-cce.21 (“Public Access is not authorized to execute service method ‘listDataEntities’”, checked with curl on 2026-10-30), and the CCE-LTER Datazoo copy needs a guest login with a name and email, which the agents correctly declined to invent. The release serves the same table openly. One host on that path, gmn.lternet.edu, was outside the raw allowlist, but it is a DataONE replica of the same restricted package.

  6. The forbidden-access audit counts URLs and paths only. The first audit matched words anywhere in a tool call, so a Haiku session grepping a provider’s web page for the word “zenodo” counted as a reach. It now matches only the URLs and paths a call uses, plus loading a CalCOFI client package (bench_tool_forbidden() in score.R, with inline checks). After the change, one call remains. A Haiku raw session on I6 (rep 3) found calcofi.io/datasets/cce-lter_zooscan/ in web-search results and tried to curl its status code. The call was refused before it ran, and calcofi.io is outside the raw allowlist in any case. The session answered NOT AVAILABLE, so no release data reached a raw answer.

Limitations

  • 24 questions is a pilot of the method, not a measurement of the release. The proposal’s benchmark has about 250 questions, an open-weights model, human baselines and a held-out set.
  • The models are all from one family (Claude). Closed-book scores also depend on what each model saw in training.
  • The reference answers come from the release under test, so a release defect shared by the reference and the release condition goes unnoticed unless the raw sessions disagree. They caught one here (finding 4); others may remain. In the full benchmark, a second scientist writes the reference code against the authoritative sources.
  • The questions were written by someone who knows the release, and most of them can be answered from the providers’ well-documented ERDDAP services. This favours neither condition by design, but it is not a sample of the questions users ask.
  • The release condition gets a plain DuckDB file with a three-line README. It has none of the AI layer the proposal would build: no MCP tools, no semantic metadata, no method register.

done

- CalBOBL bongo tows in 1972, before the bongo net replaced the ring net in 1977–78

The reference SQL for each question is in `libs/bench_ai_readiness/questions.yml`.

**Reference answers** are the question's SQL run on the release. Where the raw sessions agreed with each
other and disagreed with the release, we traced the difference to its source. In one case (finding 4
under [Raw vs. release disagreements](#raw-vs.-release-disagreements)) the release was wrong, and the
reference SQL now corrects for it. Elsewhere a legitimate difference between a provider's file and the
release still scores the raw answer wrong, so the pilot stays conservative for the raw condition.

**Sessions.** Each session is one headless Claude Code run (`claude -p`, version 2.1.314). It loads no
`CLAUDE.md`, memory, skills or MCP servers, and runs inside Claude Code's OS sandbox:

- it can write only to its own folder
- it cannot read the CalCOFI repositories, the other condition's runs or, in the raw condition, the
  release copy
- network access is limited to the providers' domains in the raw condition, and is off in the release
  condition

Every tool call is checked afterwards for any reach past the session's condition (@tbl-audit). A session
had 4 min (closed), 20 min (release) or 40 min (raw), and had to end with `FINAL ANSWER: <value>` or
`FINAL ANSWER: NOT AVAILABLE`. Numbers are scored within the tolerance stated per question, and
unanswerable items only by declining. The runner is `libs/bench_ai_readiness/run_agents.sh` and the
scorer is `libs/bench_ai_readiness/score.R`.

## Limitations

- `r n_q` questions is a pilot of the method, not a measurement of the release. The proposal's benchmark
  has about 250 questions, an open-weights model, human baselines and a held-out set.
- The models are all from one family (Claude). Closed-book scores also depend on what each model saw in
  training.
- The reference answers come from the release under test, so a release defect shared by the reference
  and the release condition goes unnoticed unless the raw sessions disagree. They caught one here
  (finding 4); others may remain. In the full benchmark, a second scientist writes the reference code
  against the authoritative sources.
- The questions were written by someone who knows the release, and most of them can be answered from
  the providers' well-documented ERDDAP services. This favours neither condition by design, but it is
  not a sample of the questions users ask.
- The release condition gets a plain DuckDB file with a three-line README. It has none of the AI layer
  the proposal would build: no MCP tools, no semantic metadata, no method register.

## Reproduce

```bash
# 1. local copy of the release (about 600 MB of parquet, plus views)
libs/bench_ai_readiness/build_release_db.sh v2026.10.21 ~/_big/bench_ai_release
# 2. sessions per configuration: questions x conditions x 3 repeats
for cfg in "sonnet-5-5 default" "sonnet-5-5 low" "opus-5-5 medium" "opus-5-5 high" "haiku-5-5 default"; do
  set -- $cfg
  libs/bench_ai_readiness/run_agents.sh "2026-10-30_$1_$2" "release raw closed" 3 6 "claude-$1" "$2"
done
# 3. this notebook: reference answers, scoring, tables
quarto render bench_ai_readiness.qmd
```

drafts. The tracked summary is `data/bench_ai_readiness/runs_2026-10-30.csv`.
